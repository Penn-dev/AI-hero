## 它能做什么

`prototype` 写的是**回答一个问题的临时代码**：状态模型用起来对不对，或这个界面应该长什么样。先有问题，再由问题决定做什么。答错了问题的原型，外观再好也是浪费。

“可丢弃”约束的是*写法*，不是承诺销毁。不写测试，不做超出能运行所需的错误处理，不抽象，不持久化数据，因为这些都无助于了解眼下唯一想知道的事。最后保留两样：答案进入正式代码，原型留在 main 之外的分支，作为答案的证据。

## 什么时候该用它

输入 `/prototype`；任务适合时，[智能体](https://www.aihero.dev/ai-coding-dictionary/agent)也会自动选用。

遇到无法光靠讨论解决的问题，就用它：状态机边界情况多到脑中推演不下，或不把三个界面放在一起就无法想象效果。[追问会话](https://www.aihero.dev/ai-coding-dictionary/grilling)常在这些问题上拖长，智能体换着问法，你不断猜测，范围越扩越大。停止追问，做出临时版本，看过后用一句话回答。如果是已建成的东西行为异常、想知道原因，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索该建什么，不诊断为什么已建的坏了。

你也可能并非主动选择而来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在路线图中创建 `prototype` 决策[任务单](https://www.aihero.dev/ai-coding-dictionary/ticket)，用本 Skill 完成。

## 两个分支

问题决定分支，两种分支产出不同：

- **“这套逻辑或状态模型用起来对吗？”** 产出**一个可分享的 HTML 文件**。页面自包含，不用构建、不用服务器，双击打开。它有带标签的状态面板，每次点击后更新；有自由尝试的按钮，可按任意顺序操作；还有分页签的**引导演示**，每个页签一个场景，下方列出按顺序要点的按钮。所有标签使用领域语言，因此可以交给设计师、产品经理或领域专家亲自尝试。页面背后的逻辑是小型纯模块，例如 reducer、状态机或一组函数，不含 DOM 代码，验证后可以直接移入正式代码。
- **“应该长什么样？”** 同一路由上放几个**结构差异很大**的界面版本，用底部悬浮栏和 `?variant=` URL 参数切换。方案必须在结构上不同，不能只换颜色；三个略作调整的卡片网格回答不了问题。尽可能放在真实页面里，使用真实数据和真实信息密度，因为放在空白页上，什么方案看起来都不错。

译注：状态模型描述对象如何随操作变化；纯模块只处理逻辑，DOM 则是网页显示结构。这里把两者分开，便于把验证过的逻辑带回正式项目。

两种方式都把状态放在内存，不用预先设置，每一步后展示完整状态。一旦开始加固，比如写测试、连真实数据库、为未来可能的情况泛化，就已经不再是在做原型。

## 原型是第一手来源

完成后留下两样东西，放在不同位置。

把**答案**，即结论以及它解决的问题，记录到持久位置，例如提交说明、ADR 或实现 issue。main 中的正式代码保留答案。

**原型**是答案来自哪里的可运行证据，不应删除，也不属于 main，因为没人维护，且很快过时。把它提交到 main 之外的临时 `prototype/<name>` 分支，永不合入；在实现 issue 上放一个指向该分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净，之后接手的人能找到并重跑原型。

## 常见问题

**等等，原型不是应该删掉吗？**

现在不是了。以前是做完、保留答案、扔掉代码。最有力的反对意见不关乎速度，而是*下个[会话](https://www.aihero.dev/ai-coding-dictionary/session)由谁接手，手上有什么依据？* 只写文字摘要，会丢掉原型最有说服力的部分。因此 Skill 现在把原型当作[第一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)，放到 main 之外的 `prototype/<name>` 分支，并让实现 issue 指向它。改变的是代码位置，不是约束，它仍永不合入 main。

译注：本页 description 仍沿用“随后删除代码”的旧措辞，而正文明确说明改为保留独立分支。本译稿保留这一来源差异，以正文说明当前文中规则。

**以前做终端程序，去哪里了？**

逻辑分支现在输出单个可分享 HTML 文件。终端程序要求使用者克隆仓库、安装运行环境，恰好排除了原型最需要听取意见的人：设计师、产品经理，以及知道状态模型应表达什么的领域专家。自包含文件双击即开，发邮件后仍能用，谁都可以操作。底下的纯逻辑模块没变，也仍是带进正式代码的部分。

**我该实现时，智能体却叫我 `/prototype`。**

这是已知命名问题。不了解流程的智能体看到 `prototype` 这个通用又有吸引力的词，会把它当成任务单出现后“显而易见的下一步”，即使设计早已谈妥也会推荐。如果已经知道做什么，下一步是逐张 `/implement`。只有明确设计问题未解决，而且讨论也解决不了时，才做原型。

**正式开发前，该不该先做整个应用的原型，比如给潜在客户演示？**

那是恰好同名的另一种产物。本 Skill 只围绕一个问题，“整个应用是什么”不是这样的单一问题。全应用原型没有自然终点，会逐渐变成正式应用：清理永远没发生，按原型规则写的无测试、无错误处理代码，就到了用户面前。需要销售演示，就有意识地按演示制作，明确其中没有生产可用代码。需要确定设计问题，就缩到那个问题。

**怎样放在独立会话里跑？**

原型位于自己的目录，会产生大量不该塞进原提问会话的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)。所以到别处做，只带答案回来。用 [handoff](https://aihero.dev/skills-handoff) 把工作交过去，再把答案带回。

**这不是最快烧 Token 的办法吗？**

可能是，如果你为本来能讨论清楚的问题做原型，或让一个原型扩张到整个功能。真正该比较的不是与零消耗比，而是 [Token](https://www.aihero.dev/ai-coding-dictionary/token) 与这种代价相比：错误状态模型已经投入生产、有调用方之后，才发现做错了。问题窄、执行短，开销才能适度。

## 出现这些迹象，就说明它在发挥作用

- 能用一句话说清原型要回答什么，并写在演示顶部，不只记在脑中。
- 不懂代码的人也能操作逻辑演示：打开文件，按页签引导点按钮，用自己的话描述结果。
- 有人说“wait, that shouldn't be possible”或“huh, I assumed X”。这是*想法*的 bug，正是原型要发现的。
- 界面版本在布局和信息层级上不同，而非只换颜色、文案。反馈会像“the header from B with the sidebar from C”。
- 一次坐下来就能得到答案。如果第二天还在开发，问题太大，应该拆分。
- 结束后，main 只有决定，没有原型；实现 issue 指向仍保存原型的分支。

中文理解：前三段英文反馈分别是“等等，这不应该能做到”“咦，我原以为是 X”，以及“用 B 的页头，配 C 的侧栏”。

## 它处在什么位置

`prototype` 是**随时可用的独立 Skill**，解决一个设计问题后，就回到原工作。其他 Skill 也会调用它。

调用最多的是 [wayfinder](https://aihero.dev/skills-wayfinder)。路线图由**决策任务单**组成，`prototype` 是四种任务类型之一，用于“应该怎样呈现”或“应该怎样表现”这类再多讨论也解决不了的问题。讨论模糊时，wayfinder 会要求做出具体东西供人判断，本 Skill 负责制作。答案解决原型任务，路线图则把原型作为资源链接起来。

其他邻居在前后两侧。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答能谈清的问题，谈不清的送到这里，一句话答案再带回访谈。下游，经过验证的状态模型或界面方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的确定输入；它可以直接嵌入原型中承载关键决定的代码片段，而不只用文字描述。其他情况可用 [ask-matt](https://aihero.dev/skills-ask-matt) 选择路线。
