`/grill-with-docs` 已成为智能体工作流中很受欢迎的计划模式替代方案。但很多人还不太会有效使用。它会不断提问，直到双方形成共同理解，而这要求**你自己也具备良好的规划能力**。

这些技能不是为了替代工程师，而是为了帮助你。本文通过九种常见失败方式，帮助你掌握它们。

> 译注：标题与开头写“九种”，原文正文按下面的主题与子主题展开，没有逐一给出九个编号。此处保留原有结构，不补造条目。模型、阈值和效率数字按作者时点与经验保留，没有重新测试。

## 理解问题：低保真与高保真

进入深入追问会话时，你的目标是回答关于将要构建之物的问题。但问题并不都一样。

![示意图：不同保真度层次的问题。](https://res.cloudinary.com/total-typescript/image/upload/v1779715889/ai-hero-images/qkcmn8yccs0rrbu5og3k.png)

| 问题类型 | 定义 | 示例 | 能靠追问解决吗 |
| --- | --- | --- | --- |
| **低保真** | 不需要详细原型或图片就能回答 | “What URL should this route live on?”（这个路由应该使用什么 URL？） | ✓ 能 |
| **高保真** | 需要放大到具体细节的图片或原型才能回答 | “How should this UI feel when we're using it?”（实际使用这个 UI 时，应该是什么感受？） | ✗ 不能 |

中文版 Prompt（学习辅助，低保真问题示例）：

```text
这个路由应该使用什么 URL？
```

中文版 Prompt（学习辅助，高保真问题示例）：

```text
实际使用这个 UI 时，应该是什么感受？
```

表单字段布局就是高保真问题的好例子。该把字段拆成多页，还是放进一张巨大的表单？要认真回答，你确实需要看到原型，或把整体做出来。

### 遇到无法靠追问解决的问题

第一个主要误区，是试图在追问会话中回答高保真问题。

遇到这类需要更具体呈现才能理解的问题时，使用**交接**模式：

1. 在第一场会话，也就是图中的蓝色会话，继续讨论低保真问题
2. 遇到高保真问题时，交给一场原型会话
3. 在独立会话中构建或做原型，以便更好地理解问题
4. 再把结果交回原来的追问会话，继续处理能靠讨论解决的问题

这个模式就是：**追问 → 原型 → 再追问**。它让你能处理高保真问题，又不打断原有讨论流程。

![追问会话与原型会话之间的交接模式。](https://res.cloudinary.com/total-typescript/image/upload/v1779715889/ai-hero-images/dkks1wlw7mkpjr0slii2.png)

## 选择合适的范围

范围，也就是你要讨论的事情有多大，极其重要。

范围过大，会出现两个问题。

**问题 1：隐藏的高保真问题**

基于已经确认能工作的东西继续构建，总比无休止地规划遥远未来容易。有人想一口气给 AI 安排好几天的任务，结果常常不理想，因为他们没有建立在自己真正理解的坚实基础上。

**问题 2：上下文窗口限制**

开始时，上下文窗口可能接近空白。但不断追问下去，会进入模型的“迟钝区”。按原文估计，对大多数前沿模型来说，大约在 120k Token 附近。超过这个位置，模型的注意力关系会吃紧，决策开始变差。

![上下文窗口逐渐填满，进入原文所称的“迟钝区”。](https://res.cloudinary.com/total-typescript/image/upload/v1779715890/ai-hero-images/yxo684qm8iwlvyx18ip1.png)

> 译注：120k 是作者给出的经验阈值，不是所有模型通用的硬性分界或本次基准测试结果。这里的“迟钝区”是形象说法。

### 拆分过大的范围

不要围绕一个巨大范围一直追问，而是在开始时就请智能体拆分：

1. 从较大范围开始
2. 让智能体拆成较小、能靠讨论解决的部分
3. 分别讨论每个小范围
4. 在这些独立会话中回答全部问题

这样就能较稳妥地待在“聪明区”，避免会话进行到一半撞上上下文限制。

![把较大范围拆成更小、更容易处理的部分。](https://res.cloudinary.com/total-typescript/image/upload/v1779715891/ai-hero-images/efw0w7wzr3xzzh6taokc.png)

## 主动参与，不要被动回答

很多很长的追问会话之所以失败，是因为人太被动。记住：**这是一场对话，不是单向采访**。

智能体负责提问，但你需要：

- 想清楚往哪里走
- 理解范围
- 确保方向不偏
- 主动引导讨论

如果太被动，智能体会用 540 个问题轰炸你，还会围绕过于低保真的事项不断追问，让范围爆炸。

但也要平衡。过于主动，也可能意味着你一直纠缠低保真细节，而此时其实应该开始写代码。如果只是不断规划，从不构建，就是追问过度了。

**找到中间点**：积极引导会话，同时知道什么时候该停止规划、开始实现。

![与智能体协作时，从被动到主动参与的光谱。](https://res.cloudinary.com/total-typescript/image/upload/v1779715891/ai-hero-images/yrglde19tasebulnsabm.png)

> 译注：540 是原文强调问题过多的具体例子，并非本次测量。“过于低保真”也按原文保留，与前文“低保真适合讨论”并存，作者此处强调对细节过度追问的问题。

## 保存设计决策

这是重要却常被忽视的失败方式。深入追问时，你正在创造一份极有价值的材料：**一个装满设计决策的上下文窗口**。

讨论结束时，你已经作出了许多关于系统如何运作的选择，写下来足有数百 Token。这些内容非常宝贵。

你可以这样处理：

- **还有上下文余量**：直接在同一会话中实现，不必交接
- **上下文快用完**：使用 `/2PRD` 技能创建产品需求文档（PRD），作为交接材料

**不要**为了写 PRD 而先清空上下文、重新开始。那是在丢掉全部设计工作。追问过程中的每个决定都有价值，应该落实成代码，或写进交接材料。

![不要在创建 PRD 之前清空上下文的提醒。](https://res.cloudinary.com/total-typescript/image/upload/v1779715892/ai-hero-images/zja4advhqmfkig5eorns.png)

> 译注：/2PRD 是固定原文中的命令名称，本文没有给出对应技能定义，不将它静默替换成其他技能。

## 用更聪明的模型来追问

用能力较弱的模型进行深入追问，是常见错误。原因如下。

追问时，你依赖两类知识：

| 知识类型 | 来源 | 可靠程度 | 主要适用阶段 |
| --- | --- | --- | --- |
| **上下文知识** | 你提供的文件、Prompt、工具结果 | 很可靠 | 实施阶段 |
| **参数知识** | 模型的训练数据与参数 | 可靠性较低，但能带来创意 | 追问阶段 |

追问时，你依靠的是模型的**参数知识**，也就是它原有的系统和应用知识，用来提出你未曾考虑的东西。假如你已经想到了，早就把它们作为上下文交过去了。

**能力弱的模型不会给你好点子**。你需要参数多的模型，通常就是大型前沿模型，才能得到有创意的建议和启发思考的问题。

但实施时可以用较小的模型，因为大部分信息已经来自上下文，例如详细计划、代码库等。

![上下文知识与参数知识的来源示意图。](https://res.cloudinary.com/total-typescript/image/upload/v1779715892/ai-hero-images/qwbrfqpigkqevehpb3mn.png)

> 译注：这是作者的选型经验，不是仅凭参数量就能判断效果的保证。上下文资料同样可能过时或错误，仍需核验；原文表格的“很可靠”不能理解为绝对正确。

## 并行开展追问会话

最后介绍一个简单而有效的技巧：**同时进行多场追问会话**。

操作方式是：

1. 你正在会话 A 中讨论
2. 智能体提出问题
3. 你回答
4. 趁它思考时，切换到会话 B
5. 回答那边的问题
6. 会话 A 准备好了，再切回去
7. 重复

这就像同时处理两个 Slack 讨论串。你不是在做很重的上下文切换，只是在管理独立对话。

**好处**：

- 吞吐量翻倍
- 用更少时间完成更多规划
- 多项设计决策可以持续推进

大多数人轻松处理的上限是两场。如果其中一场在做研究之类的长任务，也许能处理三场。随着越来越熟练，可以提高并行度。

![在两场并行追问会话之间来回切换。](https://res.cloudinary.com/total-typescript/image/upload/v1779715893/ai-hero-images/zvlogainpdjwt6bjv9cy.png)

刚接触这种工作流？从 [/grill-with-docs 中文文章](/grill-with-docs)开始，在动手前先把文档中的理解对齐。也可查看[英文原文入口](https://www.aihero.dev/grill-with-docs)。

> 译注：上段保留原技能提示框内容，改为静态链接。吞吐量翻倍与会话数量是原文经验说法，未在本次实测。

## 要点回顾

- **追问的核心是问题**。低保真问题适合讨论，高保真问题需要原型
- **范围很重要**。选择较小范围，避免耗尽上下文窗口
- **主动参与**。引导对话，也要知道何时停止规划、开始写代码
- **保留价值**。追问中作出的每个决定，都应该记录在某处
- **使用聪明的模型**。有创意的建议需要参数知识
- **并行处理**。理解各会话负责什么后，高效地在它们之间切换

越理解这些失败方式，就越能有效利用深入追问，在编码前把设计想清楚。
