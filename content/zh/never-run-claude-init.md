使用 Claude Code 或其他编程智能体时，你可能见过一个 `init` 命令，宣称能创建 `CLAUDE.md` 或 `agents.md` 文件，记录代码库的文档。

不要运行它。如果发现一份自动生成的，就删掉它。

生成的文件会消耗 Token、分散智能体注意力，而且过时得比大热天放着的梨还快。[这项研究也支持这一点](https://arxiv.org/abs/2602.11988)：不必要的上下文文件会让任务更难，而不是更容易。

> 译注：本文保留作者鲜明的观点与命令式表达，不把它改写成普遍定论。这里提供的是固定原文的研究链接，没有重新获取论文或独立验证结论，也没有删除任何文件。实际项目中的配置可能包含无法从代码发现的约束，是否精简应先审阅其内容。

## 智能体怎样使用上下文

智能体的上下文窗口会被分给几个阶段：

![上下文窗口分配示意图。](https://res.cloudinary.com/total-typescript/image/upload/v1771927533/ai-hero-images/hwhcoa9x5eg2acootps1.png)

| 阶段 | 用途 | 灵活程度 |
| --- | --- | --- |
| **系统提示** | LLM 指令、MCP 服务器、系统工具、`CLAUDE.md` 内容 | 不灵活，启动时固定 |
| **探索** | 了解代码库里有什么 | 很灵活 |
| **实现** | 编写和修改文件 | 很灵活 |
| **测试** | 运行测试、调试、反馈循环 | 很灵活，遇到问题时可能急剧膨胀 |

探索、实现和测试的份量都可调整。简单任务不需要太多探索，没有缺陷的实现也不需要太多测试。

但系统提示在**智能体启动的那一刻就固定下来了**。`CLAUDE.md` 里的所有内容都会让它膨胀，挤占真正完成工作所需的空间。

缩小系统提示，就能腾出更多空间做实际工作，也能降低成本。

> 译注：表格是作者对工作流程的概括，不代表所有智能体都按相同方式加载上下文。“没有缺陷就少测”也是原文论述，并不能替代验证实现是否有缺陷。

## 指令预算

LLM 不只有上下文窗口，还有**指令预算**：它能同时遵循多少条指令，也存在限度。

`CLAUDE.md` 中的每句话都是一条指令。按作者的估计，LLM 实际上一次能处理约 **300 到 400 条指令**，更大的模型也许能到 500 条。

如果你往 `CLAUDE.md` 塞了几十条不相关的指令，智能体还没开始任务，预算就已经被消耗了。

> 译注：上述条数是原文经验性数字，不是所有模型都适用的统一硬上限；文件中的每句话也不一定都是独立操作指令，原文借此强调无关上下文的成本。

## 全局性问题

常见建议是：智能体做了你不喜欢的事，就往 `CLAUDE.md` 加一条规则。

也许它用了 npm，而不是 pnpm；也许它采用了你讨厌的 React 模式。于是你加上一行。

问题是，`CLAUDE.md` 是全局性的。每条指令都会影响每次会话：前端、后端、文档、数据库，全都包括在内。

![前端、后端、文档等不同类型的请求。](https://res.cloudinary.com/total-typescript/image/upload/v1771927533/ai-hero-images/l9gyebsbhaf0fmhql96c.png)

那条 React 规则对前端会话有用，但下一次也许只做后端，它就完全无关了；再下一次可能又是文档任务。

每增加一行，就增加一份成本，并在每次会话中反复累积，不管它是否相关。

> 译注：这里的“全局”沿用作者对反复加载上下文的说法；具体文件作用域、层级和加载规则需要根据工具与项目配置判断，不能一概视为跨所有项目生效。

## Init 实际会生成什么

Init 命令往往生成相同几类内容，每类都有问题。

**命令列表**。Init 很爱把 `package.json` 中的每个脚本都倒进文件。这些信息很容易找到，智能体直接读 `package.json` 就行。你却在花 Token 复制真正的信息来源。

**架构说明**。框架名称、渲染模式、编译器配置，智能体都能从配置文件和导入语句中发现。`react-router.config` 已经告诉它项目在用 React Router，`effect` 的导入也告诉它项目在用 Effect。

**文件与服务引用**。这是最糟糕的一类。Init 会记录具体文件、服务以及它们的关系。一旦重命名文件、移动服务或改变实现，这份文档就错了，甚至会主动把智能体引向错误方向。

**实现模式**。具体功能如何工作、哪里应该采用什么模式。这些不仅能从代码中发现，也只与少数会话相关。大部分任务都不会触及大部分模式。

共同的问题是：init 生成的内容，要么很容易从源代码中找到，要么很快会过时。文件系统本身就是文档。如果结构合理，智能体会直接从真实来源了解架构，而不是依赖一份不断失效的摘要。

## 解决办法

### 相信探索步骤

现代编程智能体都有探索阶段。修改之前，它会读文件、搜索代码库，只为眼前的任务及时建立所需上下文。

这比静态的 `CLAUDE.md` 更好，因为它只加载相关内容，而且总能反映代码的当前状态。

### 用技能引导行为

有些引导确实有用。比如，希望智能体在处理复杂 UI 状态时优先使用 reducer，或者遵循某种测试模式。

这些内容应该放进**技能**：智能体可以发现这些指令，在相关时加载，而不必让每次会话都为它消耗指令预算。

### 让 CLAUDE.md 接近空白

如果基础配置信息不该放在 `CLAUDE.md`，行为引导又该放进技能，那还剩什么？

几乎没什么。我的整个 `CLAUDE.md` 只有：

```
you are on WSL on Windows
```

中文版 Prompt（学习辅助，完整对应原文环境提示）：

```text
你正在 Windows 上的 WSL 环境中运行。
```

英文只有六个词。保留它，是因为 WSL 有些不直观的路径解析问题，智能体无法自己发现。标准就是这样：只放那些既无法自行发现、又对所有任务都相关的信息。

## 最后的结论

不要运行 init。它生成的文件会把无关信息塞进全局上下文，扩大系统提示，浪费指令预算，并在代码变化时立即过时。

你最终要么不断花 Token 维护它，要么把它删掉。不如直接跳到删除这一步。

**相信探索步骤，用技能引导行为，让 `CLAUDE.md` 接近空白。**
